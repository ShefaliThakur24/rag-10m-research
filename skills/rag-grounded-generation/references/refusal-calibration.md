# Refusal calibration (reference)

Refusal is a **knob**, not a switch. The Pareto frontier is false-refusal rate vs. hallucination rate; the operating point is a product decision. This reference is the recipe for choosing that operating point and keeping it calibrated as traffic shifts.

## 1. Three-signal OR refusal logic (formal)

Refusal fires when **any** of these is true:

```
refuse(q, chunks, draft) := 
      ( max_i sim(q, chunk_i)        < τ_sim   [class(q)] )   # signal (a)
   OR ( max_i rerank(q, chunk_i)     < τ_rerank[class(q)] )   # signal (b)
   OR ( entailment(⋃chunks, draft) ∈ {not_supported, partial} ) # signal (c)
```

Why OR and not AND:
- **AND collapses to "never refuse"** — at least one signal will always pass on any non-adversarial query.
- **Single signal misses the failure split** — signal (a)/(b) catch retriever failures (no relevant chunk); signal (c) catches generator failures (chunk exists but draft doesn't follow from it). You need both halves.

Edge case: when signal (a) and (b) both pass but (c) fires repeatedly on the same query class, you've found a **generator regression**, not a retrieval issue. Route to the diagnostic matrix in `SKILL.md`.

## 2. Per-query-class threshold calibration (recipe)

Single global thresholds leave 2-3× precision on the table. Per-class calibration captures that lift.

```python
# 1. Cluster recent traffic by query embedding (e.g. k=8-32 via mini-batch k-means)
clusters = kmeans(query_embeddings, k=16)

# 2. For each cluster, fit τ_sim and τ_rerank to target a 5-15% refusal rate
#    against a held-out batch with gold (answerable | unanswerable) labels.
for c in clusters:
    queries_c = traffic[c]
    labels_c  = gold_answerable_labels[c]  # 1 = answerable, 0 = unanswerable

    # Sweep τ; choose the one maximizing F1 subject to refusal_rate ∈ [0.05, 0.15]
    τ_sim[c]    = argmax_τ f1(predict_refuse(queries_c, τ_only_sim=τ),    labels_c)
    τ_rerank[c] = argmax_τ f1(predict_refuse(queries_c, τ_only_rerank=τ), labels_c)

# 3. Recalibrate weekly or on traffic-distribution drift (KL divergence > 0.1
#    between week-over-week query-embedding histograms).
```

Cold start (no labeled traffic): start with a single global τ, build a manual review queue from refused responses, promote to per-class once you have a few hundred labeled examples per cluster.

## 3. Refusal Tokens + post-hoc temperature scaling

[arXiv:2412.06748](https://arxiv.org/abs/2412.06748) introduces Refusal Tokens — a test-time-tunable strategy: train (or fine-tune) the model with a special `[refuse]` token and threshold its emission probability at decode time. Refusal sensitivity becomes a single knob — no retraining when the operating point shifts.

Pair with **post-hoc softmax temperature scaling** (τ=2 over the refuse-token logit) for calibration:

```
adjusted_ECE: 0.13 → 0.08
```

Temperature scaling is one scalar fit on a held-out dev set; it does not change decisions, it calibrates the **probabilities** so the threshold can be read in real units. Without it, the refuse-token probability is ordinally meaningful but not calibrated.

When refusal-token fine-tuning isn't available (closed-weight models, no SFT budget), fall back to signal (c) — entailment-based refusal — and treat it as the equivalent of the refuse-token threshold.

## 4. Constructive refusal templates

Blank "I cannot answer" destroys trust; **constructive refusal** preserves it. Three patterns by domain:

### General / B2B SaaS

```
I don't have enough information about <SPECIFIC_GAP> in the knowledge base.

The closest related material I found is <DOC_TITLE> (<DOC_ID>#<CHUNK_ID>),
which discusses <CLOSEST_TOPIC> but does not address <QUERY_ASPECT>.

You might try:
- rephrasing the question to focus on <CLOSEST_TOPIC>
- broadening the scope to include <RELATED_AREA>
- escalating to <HUMAN_ROUTE> for hands-on help
```

### Customer support (narrow domain)

```
I couldn't find <SPECIFIC_GAP> in our help docs.

The closest article is "<DOC_TITLE>" — it covers <CLOSEST_TOPIC>, but if your
question is about <QUERY_ASPECT>, that's outside what I have available.

Want me to open a ticket with our support team?
```

### Regulated / medical / financial

```
I can't provide an answer on this. The information available to me does not
sufficiently cover <SPECIFIC_GAP>, and on this topic I will not infer beyond
what is explicitly stated in the source material.

Please consult <ESCALATION_ROUTE: clinician / compliance team / advisor> for
authoritative guidance.
```

The constructive refusal is generated by the model under the same structured-output schema (`refusal: true`, `refusal_reason: "..."`) — not a template string substitution. The schema guarantees the response shape; the prompt guarantees the tone.

Anti-pattern: **never** name "closest related material" in compliance contexts where the title alone could leak sensitive info (e.g. "I found nothing about your account, but here's a doc about account closures"). Use the regulated template in those domains.

## 5. Healthy refusal rate by domain

Track refusal rate as a first-class metric. Per-domain healthy bands (practitioner consensus — Hamel Husain evals FAQ, EACL 2026 taxonomy):

| Domain | Healthy refusal rate | If outside, look at |
|---|---|---|
| **General enterprise / B2B SaaS** | **5-15%** | 0% → hallucinating on OOD; >30% → retrieval coverage is the bottleneck (raise k, improve chunking, add hybrid retrieval) |
| **Regulated: medical / legal / financial** | **15-25%** | <10% → faithfulness gate is too loose, raise τ_entailment; >35% → corpus coverage gap, escalate to human triage |
| **Customer support (narrow product domain)** | **2-8%** | High refusal on the happy path = retriever or chunking issue, not generator; sample refusals and label them retrieval-bottleneck vs generator-bottleneck |
| **Search-style / "best-effort" UI** | **0-2%** | This is the regime where cite-or-refuse is overkill — relax to signal (a) only and surface a confidence band, not a hard refusal |

**Diagnostic when the rate drifts:**

- Sudden rate ↑ with no model change → upstream traffic shift; re-cluster query classes, refit τ.
- Slow rate ↑ over weeks → corpus is getting stale relative to query distribution; refresh ingestion.
- Rate ↓ after model version bump → new generator is more confident (often less calibrated); re-tighten signal (c) τ_entailment.
- Rate ↑ after retriever swap → embedding or rerank model changed scale; refit τ_sim and τ_rerank, do not just translate.

Refusal rate is not a target to minimize. A 0% refusal rate on a 10M-doc corpus means the system is hallucinating on out-of-domain queries — a worse failure than a tracked, calibrated refusal.
